## Story

**As an** HR Admin,  
**I want** the One field to show yellow for 24 hours then turn green,  
**So that** I know when the mandatory waiting period has elapsed.

## Acceptance Criteria

1. Database adds `one_marked_at` TIMESTAMPTZ column to employees table
2. When One field is set to true, record current timestamp in `one_marked_at`
3. Display yellow badge ("⚠ Pending") when One=true and < 24 hours elapsed since `one_marked_at`
4. Display green badge ("✓ Complete") when One=true and >= 24 hours elapsed
5. Badge updates automatically via polling (every 60 seconds) or real-time subscription
6. Tooltip on yellow badge shows "Pending - Will be ready in X hours"
7. If One field is set to false, clear `one_marked_at` timestamp
8. If One field is toggled true → false → true, reset `one_marked_at` to new timestamp
9. Time calculation accounts for timezone differences correctly (use UTC)
10. API endpoint returns current status (yellow/green) based on elapsed time calculation
11. Client-side logic calculates status in real-time for immediate feedback
12. Edge case: Handle clock skew and daylight savings time correctly

### Business Logic Service

**File Location:** `src/lib/services/one-field-status.ts`

**Function Specifications:**

```typescript
/**
 * Calculate the current status of the One field based on elapsed time since marking.
 *
 * Business Rule: One field must remain true for 24 hours before Talmundo field can be edited.
 * This enforces a mandatory waiting period for external system synchronization.
 *
 * @param oneValue - Current boolean value of the One field
 * @param markedAt - Timestamp when One was set to true (UTC)
 * @returns 'green' if >= 24 hours elapsed, 'yellow' if < 24 hours, null if One is false
 */
export function getOneFieldStatus(
  oneValue: boolean,
  markedAt: Date | null
): 'green' | 'yellow' | null {
  if (!oneValue) return null;
  if (!markedAt) return 'yellow'; // Just marked, timestamp not saved yet

  const now = new Date();
  const elapsed = now.getTime() - markedAt.getTime();
  const twentyFourHours = 24 * 60 * 60 * 1000; // milliseconds

  return elapsed >= twentyFourHours ? 'green' : 'yellow';
}

/**
 * Calculate remaining time until One field status turns green.
 *
 * @param markedAt - Timestamp when One was set to true
 * @returns Formatted string "X hours Y minutes" or "Ready" if time elapsed
 */
export function getRemainingTime(markedAt: Date): string {
  const now = new Date();
  const elapsed = now.getTime() - markedAt.getTime();
  const twentyFourHours = 24 * 60 * 60 * 1000;
  const remaining = twentyFourHours - elapsed;

  if (remaining <= 0) return 'Ready';

  const hours = Math.floor(remaining / (60 * 60 * 1000));
  const minutes = Math.floor((remaining % (60 * 60 * 1000)) / (60 * 1000));

  if (hours === 0) return `${minutes} minutes`;
  return `${hours} hours ${minutes} minutes`;
}
```

**Timezone Handling:**

- All timestamps stored in UTC in database (TIMESTAMPTZ type)
- JavaScript Date objects automatically handle timezone conversion
- Calculations performed in UTC to avoid daylight savings time issues
- Client display may show local time, but elapsed time calculation is always UTC-based

### Real-Time Updates

**Polling Strategy:**

Use `setInterval` in EmployeeTable component to recalculate status every 60 seconds:

```typescript
useEffect(() => {
  const interval = setInterval(() => {
    // Force table re-render by updating a dummy state
    // This will recalculate getOneFieldStatus for all visible rows
    setRefreshTrigger((prev) => prev + 1);
  }, 60000); // 60 seconds

  return () => clearInterval(interval);

```

**Alternative - Supabase Real-Time:**

Subscribe to `employees` table changes for `one_marked_at` column:

```typescript
useEffect(() => {
  const channel = supabase
    .channel('one-field-updates')
    .on(
      'postgres_changes',
      {
        event: 'UPDATE',
        schema: 'public',
        table: 'employees',
        filter: `one_marked_at=not.is.null`,
      },
      (payload) => {
        // Update local state when one_marked_at changes
        refreshEmployeeData();
      }

    .subscribe();

  return () => {
    supabase.removeChannel(channel);
  };
}, []);
```

**Performance Consideration:** Polling every 60 seconds is lightweight and sufficient for this use case. Real-time subscription adds complexity and may not be necessary since the 24-hour window provides coarse-grained timing.

### Technical Constraints

**Performance Considerations:**

- Status calculation is O(1) - simple arithmetic on timestamps
- Polling every 60 seconds adds negligible overhead (<10ms per render)
- No database queries needed for status calculation (timestamp already fetched)

**Timezone Handling:**

- PostgreSQL TIMESTAMPTZ stores all timestamps in UTC
- JavaScript Date object handles timezone conversion automatically
- Elapsed time calculation uses UTC timestamps, avoiding DST issues
- Display format can be localized, but calculation remains UTC-based

**Edge Cases:**

1. **Clock Skew:** If server clock differs from client clock by >1 hour, status calculation may be slightly off. Mitigation: Use server-calculated status as source of truth in API responses.

2. **Daylight Savings Time:** Using UTC timestamps eliminates DST issues. The 24-hour period is always 86,400,000 milliseconds regardless of local time changes.

3. **Concurrent Updates:** If two users toggle One field simultaneously, last-write-wins. Database timestamp reflects the most recent change.

4. **Null Timestamp:** If `one_marked_at` is null but `one` is true (data inconsistency), display yellow badge and log warning. This should not occur in normal operation due to API validation.

### Business Rule Clarification

**Context: Talmundo System Integration**

The One field represents a completion checkpoint that triggers data synchronization to the **Talmundo external system**. Talmundo's integration requirements mandate a **24-hour processing window** after the One field is marked as complete before dependent fields (like Talmundo itself) can be edited.

This waiting period ensures:

1. Data synchronization completes successfully
2. External system validations run
3. Integration errors surface before proceeding

The yellow → green badge progression provides visual feedback to HR admins on the synchronization status, preventing premature editing of dependent fields and reducing integration errors.
