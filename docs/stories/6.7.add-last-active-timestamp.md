**As an** HR Admin,  
**I want** to see when each user was last active in the system,  
**so that** I can identify inactive accounts and manage user access.

1. **Database Schema:**
   - Add `last_active_at` column to `users` table (timestamp, nullable)
   - Migration script to add column

2. **Activity Tracking:**
   - Middleware updates `last_active_at` timestamp on every authenticated request
   - Timestamp update happens asynchronously (non-blocking)
   - Update only if last activity > 5 minutes ago (avoid excessive DB writes)

3. **User Management Table:**
   - Add "Last Active" column to User Management table
   - Display relative time: "2 hours ago", "3 days ago", "Never" (if null)
   - Sort by Last Active (newest first by default)

4. **API Endpoint:**
   - PATCH `/api/admin/users/[id]/update-activity` (internal use by middleware)

5. **Performance:**
   - Activity update uses optimistic locking or upsert pattern
   - No impact on page load time (<10ms overhead)

6. **Privacy:**
   - Last Active timestamp only visible to HR Admin role
   - Other users cannot see their own or others' activity

7. **Translations:**
   - "Last Active" column header translated
   - Relative time strings translated (next-intl provides this via `relativeTime` formatter)

### Middleware Implementation Pattern

[Source: middleware.ts, docs/architecture/backend-architecture.md#middlewareguards]

**Current Middleware Flow:**

```typescript
export async function middleware(request: NextRequest) {
  const supabase = createServerClient(...);
  const { data: { user } } = await supabase.auth.getUser();

  }

  // Continue request

```

**Updated Middleware Flow (with activity tracking):**

```typescript
// middleware.ts (with activity tracking)
import { shouldUpdateActivity } from '@/lib/server/utils/activity-tracker';
import { userRepository } from '@/lib/server/repositories/user-repository';

export async function middleware(request: NextRequest) {
  const supabase = createServerClient(...);
  const { data: { user: authUser } } = await supabase.auth.getUser();

  if (!authUser) {
    // Redirect to login
  }

  // Fetch application user record
  const { data: appUser } = await supabase
    .from('users')
    .select('*')
    .eq('auth_user_id', authUser.id)
    .single();

  // Track activity asynchronously (non-blocking)
  if (appUser && shouldUpdateActivity(appUser.last_active_at)) {
    // Fire-and-forget update (don't await)
    userRepository.updateLastActive(appUser.id).catch((error) => {
      console.error('Failed to update user activity:', error);
      // Silently fail - activity tracking failure shouldn't break requests
    });
  }

  // Continue request immediately
  return response;
}
```

**Activity Throttling Logic:**

```typescript
// src/lib/server/utils/activity-tracker.ts
export function shouldUpdateActivity(lastActive: string | null): boolean {
  if (!lastActive) return true; // Never updated before

  const lastActiveTime = new Date(lastActive).getTime();
  const now = Date.now();
  const fiveMinutesMs = 5 * 60 * 1000;

  return now - lastActiveTime > fiveMinutesMs;
}
```

**Why 5-Minute Throttle?**

- Reduces database writes by ~90% for active users
- Prevents excessive load during browsing sessions
- Balances accuracy with performance
- Still provides useful "last seen" granularity for admin purposes

### Performance Considerations

**Middleware Overhead Target:** <10ms

**Optimization Strategies:**

1. **Fire-and-Forget Updates:**
   - Don't await database write
   - Update happens asynchronously in background
   - Request proceeds immediately without waiting

2. **5-Minute Throttle:**
   - Reduces write frequency by ~90%
   - Active user browsing for 1 hour = 12 updates instead of ~120

3. **Database Index:**
   - Index on `last_active_at DESC NULLS LAST` for efficient sorting
   - Query performance remains fast even with thousands of users

4. **Silent Failure:**
   - Activity tracking errors don't propagate to user
   - Logs error for debugging but continues request
   - System remains functional even if activity tracking breaks

**Measurement:**


### Known Issues and Edge Cases

**Edge Case 1: Simultaneous Requests**

- **Scenario:** User opens multiple tabs, simultaneous requests update `last_active_at`
- **Solution:** Last write wins (acceptable for activity tracking)
- **Impact:** Timestamp may flicker between requests, but within milliseconds

**Edge Case 2: Clock Skew**

- **Scenario:** Server clock differs from database clock
- **Solution:** Use database's `NOW()` function for timestamp (server-side)
- **Impact:** No issue, database generates timestamp

**Edge Case 3: Null Sorting**

- **Scenario:** Users who never logged in have null `last_active_at`
- **Solution:** SQL: `ORDER BY last_active_at DESC NULLS LAST`
- **Impact:** Never-active users appear at bottom of sorted list

**Edge Case 4: Very Old Timestamps**

- **Scenario:** User inactive for months/years
- **Solution:** Display "X months ago", "X years ago" (next-intl handles this)
- **Fallback:** If >5 years, consider showing absolute date

**Edge Case 5: Middleware Failure**

- **Scenario:** Database unreachable, activity update fails
- **Solution:** Catch error silently, log, continue request
- **Impact:** Activity tracking paused temporarily, resumes when DB recovers
