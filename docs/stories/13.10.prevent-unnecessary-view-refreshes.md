# Story 13.10: Prevent Unnecessary View Refreshes

## Status

**In progress** (Review done, see notes)

---

## Story

**As a** HR Admin user,  
**I want** the view to only refresh when actual data changes occur,  
**so that** I don't experience unnecessary flickering or data reloading when I click without making changes.

---

## Acceptance Criteria

**Given** I click on an inline editable field in an employee row  
**When** I click somewhere else without changing the field value  
**Then** the view does NOT refresh  
**And** no API call is made to update the employee  
**And** the field returns to its original state (not in edit mode)

**Given** I click on an inline editable field and change its value  
**When** I click somewhere else  
**Then** the view refreshes to show the updated value  
**And** an API call is made to save the change  
**And** the updated data is displayed

**Given** I click somewhere on the dashboard (not on an input field)  
**When** no data values are actually changed  
**Then** the view does NOT refresh  
**And** no unnecessary API calls are made

**Given** I click on a button that doesn't modify employee data (e.g., "Search", filter checkbox)  
**When** the button action completes  
**Then** only the necessary view updates occur (e.g., filter results update)  
**And** no full table refresh happens unless data actually changed

**Given** I am editing an inline field  
**When** I press Escape to cancel editing  
**Then** the field value reverts to original  
**And** no API call is made  
**And** the view does NOT refresh

## Dev Notes

### Change Detection Implementation

```typescript
export function hasValueChanged(original: any, current: any): boolean {
  // Handle null/undefined
  if (original === null || original === undefined) {
    return current !== null && current !== undefined;
  }
  if (current === null || current === undefined) {
    return original !== null && original !== undefined;
  }
  
  // Handle dates
  if (original instanceof Date && current instanceof Date) {
    return original.getTime() !== current.getTime();
  }
  
  // Handle strings (trim whitespace)
  if (typeof original === 'string' && typeof current === 'string') {
    return original.trim() !== current.trim();
  }
  
  // Default comparison
  return original !== current;
}
```

### Inline Edit Handler Pattern

```typescript
const handleFieldUpdate = async (employeeId: string, field: string, newValue: any) => {
  const originalValue = getOriginalValue(employeeId, field);
  
  // Check if value actually changed
  if (!hasValueChanged(originalValue, newValue)) {
    // Cancel edit mode, no API call
    cancelEditMode(employeeId, field);
    return;
  }
  
  // Value changed, save it
  await saveFieldUpdate(employeeId, field, newValue);
  // Refresh view to show updated value
  refreshEmployeeData(employeeId);
};
```

### Escape Key Handler

```typescript
const handleKeyDown = (event: React.KeyboardEvent, employeeId: string, field: string) => {
  if (event.key === 'Escape') {
    event.preventDefault();
    cancelEditMode(employeeId, field);
    // Revert to original value, no API call
  }
};
```

### Summary

The implementation successfully adds change detection to prevent unnecessary view refreshes when inline editing fields. The core functionality is solid with comprehensive test coverage. However, one area requires attention: real-time updates from Supabase subscriptions don't verify if data actually changed before updating state, which could cause unnecessary re-renders.

### Key Findings

#### HIGH Severity Issues

None

#### MEDIUM Severity Issues

1. **Real-time updates don't check for actual changes** [file: src/lib/hooks/use-employees.ts:290-296]
   - The `handleRealtimeEvent` function updates employee state whenever an UPDATE event is received, even if the data hasn't actually changed
   - This could cause unnecessary re-renders when Supabase sends update events for unchanged data
   - **Recommendation:** Add change detection using `hasValueChanged` to compare old and new employee data before updating state

#### LOW Severity Issues

1. **Task description clarification needed** [file: docs/stories/13.10.prevent-unnecessary-view-refreshes.md:60-66]
   - Task 1.2 mentions adding change detection to `handleMasterdataUpdate` and `handleCustomDataUpdate`
   - However, change detection is correctly implemented at the component level (EditableCell) before calling these handlers
   - This is the correct architectural approach, but the task description could be clearer
