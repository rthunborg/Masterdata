# Story 8.7: Important Dates Capacity Management

## Status

**Approved**

---

## Story

**As an** HR Admin,  
**I want** important dates to track max_spots and remaining_spots,  
**So that** I prevent overbooking training dates and manage capacity effectively.

---

## Acceptance Criteria

1. Database adds `max_spots` INTEGER and `remaining_spots` INTEGER columns to `important_dates` table
2. Default values set based on category: ÖMC=20, Stena=99, PE3=1
3. When creating new important date, `remaining_spots` initializes to `max_spots` value
4. When employee is assigned to a date (omc_date, stena_date, or pe3_date set), decrement `remaining_spots` by 1 atomically
5. When employee's date is changed or cleared, increment `remaining_spots` for old date by 1 atomically
6. Transaction handling ensures concurrency safety using row-level locks (SELECT FOR UPDATE) to prevent negative `remaining_spots`
7. Important Dates table displays `max_spots` and `remaining_spots` columns (sortable, filterable)
8. Visual warning when `remaining_spots` reaches 0 (red badge "Full" or "Fully Booked")
9. Visual warning when `remaining_spots` < 5 (yellow badge "Almost Full")
10. API validation prevents assigning employee to date with `remaining_spots` = 0 (server-side enforcement)
11. Bulk operations (CSV import, termination workflows) correctly update `remaining_spots` atomically using database transactions
12. Edge case: If date is deleted, handle employee assignments gracefully (clear employee date fields, recalculate capacity)

### Architecture Context

This story implements capacity management for the Important Dates system, preventing overbooking of training dates by tracking maximum capacity (`max_spots`) and remaining availability (`remaining_spots`) for each date. The system uses database transactions with row-level locks to ensure concurrency safety when multiple HR admins assign employees simultaneously.

The Important Dates table already displays date records with sortable columns. Story 8.7 adds `max_spots` and `remaining_spots` columns with visual capacity indicators.

### Business Logic Service

**File Location:** `src/lib/services/date-capacity.ts`

**Function Specifications:**

```typescript
/**
 * Validate if an employee can be assigned to a date based on remaining capacity.
 *
 * @param dateId - UUID of the important date record
 * @param dateType - Type of date field being assigned
 * @returns true if spots available (remaining_spots > 0), false if fully booked
 */
export async function canAssignEmployeeToDate(
  dateId: string,
  dateType: 'omc_date' | 'stena_date' | 'pe3_date'
): Promise<boolean> {
  const { data: date } = await supabase
    .from('important_dates')
    .select('remaining_spots')
    .eq('id', dateId)
    .single();

  return date ? date.remaining_spots > 0 : false;
}

/**
 * Atomically assign an employee to a date with capacity management.
 * Uses database transaction to ensure concurrency safety and prevent overbooking.
 *
 * Transaction steps:
 * 1. Lock old and new date rows (SELECT FOR UPDATE)
 * 2. If old date exists, increment remaining_spots by 1
 * 3. Decrement new date remaining_spots by 1
 * 4. Check constraint (remaining_spots >= 0)
 * 5. Update employee date field
 * 6. Commit or rollback on constraint violation
 *
 * @param employeeId - UUID of employee being assigned
 * @param newDateId - UUID of date to assign employee to
 * @param oldDateId - UUID of previous date (null if new assignment)
 * @param dateType - Type of date field ('omc_date', 'stena_date', 'pe3_date')
 * @returns Success object or throws error if fully booked
 */
export async function assignEmployeeToDate(
  employeeId: string,
  newDateId: string,
  oldDateId: string | null,
  dateType: 'omc_date' | 'stena_date' | 'pe3_date'
): Promise<{ success: boolean; message: string }> {
  // Use Supabase RPC function for atomic transaction
  const { data, error } = await supabase.rpc('update_date_spots', {
    employee_id: employeeId,
    new_date_id: newDateId,
    old_date_id: oldDateId,
    date_type: dateType,
  });

  if (error) {
    if (error.message.includes('No remaining spots')) {
      throw new Error(
        'Cannot assign employee - date is fully booked (0 spots remaining)'
      );
    }
    throw error;
  }

  return { success: true, message: 'Employee assigned successfully' };
}

/**
 * Release date capacity when employee is terminated or date assignment is cleared.
 * Increments remaining_spots for the specified date.
 *
 * @param dateId - UUID of date to release capacity for
 * @returns Success status
 */
export async function releaseDateCapacity(dateId: string): Promise<void> {
  await supabase
    .from('important_dates')
    .update({ remaining_spots: supabase.sql`remaining_spots + 1` })
    .eq('id', dateId);
}
```

**RPC Function (SQL):**

```sql
CREATE OR REPLACE FUNCTION update_date_spots(
  employee_id UUID,
  new_date_id UUID,
  old_date_id UUID,
  date_type TEXT
)
RETURNS VOID AS $$
DECLARE
  remaining INT;
BEGIN
  -- Lock rows to prevent concurrent modification
  PERFORM id FROM important_dates
  WHERE id IN (new_date_id, old_date_id)
  FOR UPDATE;

  -- Increment old date spots if exists
  IF old_date_id IS NOT NULL THEN
    UPDATE important_dates
    SET remaining_spots = remaining_spots + 1
    WHERE id = old_date_id;
  END IF;

  -- Decrement new date spots
  UPDATE important_dates
  SET remaining_spots = remaining_spots - 1
  WHERE id = new_date_id
  RETURNING remaining_spots INTO remaining;

  -- Check if spots available (constraint check)
  IF remaining < 0 THEN
    RAISE EXCEPTION 'No remaining spots available for this date';
  END IF;

  -- Update employee date field
  EXECUTE format('UPDATE employees SET %I = $1 WHERE id = $2', date_type)
  USING new_date_id, employee_id;
END;
$$ LANGUAGE plpgsql;
```

### Concurrency & Transaction Handling

**Problem:** Two HR admins simultaneously assign employees to the last remaining spot on a date → both succeed → negative `remaining_spots` (data corruption).

**Solution:** PostgreSQL row-level locks with `SELECT FOR UPDATE` in transaction.

**Implementation:**

```sql
BEGIN;
  -- Lock the date row exclusively (other transactions wait)
  SELECT remaining_spots FROM important_dates WHERE id = ? FOR UPDATE;

  -- Decrement spots
  UPDATE important_dates SET remaining_spots = remaining_spots - 1 WHERE id = ?;

  -- Check constraint (fails if remaining_spots < 0)
  -- PostgreSQL automatically rolls back on constraint violation

  -- Update employee assignment
  UPDATE employees SET omc_date = ? WHERE id = ?;
COMMIT;
```

**Behavior:**

- Transaction 1 locks date row, decrements spots to 0, commits
- Transaction 2 waits for lock, then attempts to decrement spots to -1
- CHECK constraint violation occurs, transaction 2 rolls back
- Transaction 2 returns error to user: "Date fully booked"

**Performance Consideration:**
Row-level locks are lightweight and only block concurrent updates to the same date row. Updates to different dates proceed in parallel without blocking.

### Technical Constraints

**Performance Considerations:**

- Row-level locks only block concurrent updates to same date row (different dates proceed in parallel)
- Transaction overhead: ~5-10ms per assignment (acceptable for user interactions)
- Query optimization: Index on `important_dates.id` (primary key, automatically indexed)
- Date dropdown query: Fetch all dates with `remaining_spots > 0` (filtered in SQL for efficiency)

**Capacity Defaults by Category:**

- **ÖMC**: max_spots = 20 (large training sessions)
- **Stena**: max_spots = 99 (effectively unlimited for operational dates)
- **PE3**: max_spots = 1 (one-on-one appointments)

**Edge Cases:**

1. **Date Deletion with Assigned Employees:** Clear all employee date fields referencing deleted date (set to NULL). No need to update `remaining_spots` since date is deleted.

2. **Concurrent Assignments to Last Spot:** Use row-level locks to prevent negative `remaining_spots`. Second assignment fails with error message.

3. **Bulk Import Exceeding Capacity:** Process imports sequentially within transaction. If date becomes full during import, skip remaining assignments to that date and log errors.

4. **Changing Date Assignment:** Atomically increment old date spots and decrement new date spots in single transaction (no intermediate state where spots are incorrect).

5. **Null Date Values:** If employee date field is NULL (no assignment), no spot tracking needed. Setting date from NULL to value decrements spots. Setting date from value to NULL increments spots.

### Business Rule Clarification

**Context: Training Date Capacity Management**

Important dates represent scheduled training sessions, operational events, and one-on-one appointments with **limited capacity**. Each date category has different capacity requirements:

1. **ÖMC Training Dates**: Large group training sessions with **20 participant capacity** (classroom/facility limit)
2. **Stena Operational Dates**: General scheduling dates with **99 capacity** (effectively unlimited for operational planning)
3. **PE3 Appointments**: One-on-one sessions with **1 participant capacity** (single-person appointments)

**Capacity Tracking Prevents:**

- Overbooking training sessions beyond facility capacity
- Double-booking one-on-one appointments
- Manual spot counting errors
- Data inconsistency when multiple HR admins assign employees concurrently

**Visual Feedback Requirements:**

- **Red Badge "Full"**: When `remaining_spots = 0`, prevent new assignments
- **Yellow Badge "Almost Full"**: When `remaining_spots < 5`, warn HR admin to review capacity
- **No Badge**: When sufficient capacity available (>= 5 spots)

**Atomic Transaction Requirement:**
The system MUST use database transactions with row-level locks to prevent race conditions. Without transactions, concurrent assignments can result in negative `remaining_spots` (data corruption). This is critical for data integrity.
