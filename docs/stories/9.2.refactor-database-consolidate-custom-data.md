# Story 9.2: Refactor Database Architecture - Consolidate Custom Column Data

## Status **Done**

**Implementation Complete - Awaiting Manual Testing**

---

## Story

**As a** Technical Lead,  
**I want** custom column data consolidated into the employees table instead of separate party-specific tables,  
**so that** the architecture is simpler, more maintainable, and eliminates complex multi-table operations.

---

## Background & Context

### Current Architecture Problems

The current system stores custom column data in **four separate party-specific tables** (sodexo_data, omc_data, payroll_data, toplux_data), each with:

- employee_id (foreign key)
- data (JSONB storing custom column values)

This design creates significant complexity:

1. **HR Admin Operations Are Complex**: When HR Admin (who sees all parties' data) edits a custom column, the system must:
   - Query all 4 tables to find where data exists
   - Merge data from multiple tables
   - Update/insert across multiple tables
   - Track success/failure for each operation

2. **Inconsistent Permission Model**:
   - Masterdata columns stored directly in employees table with role permissions in column_config
   - Custom columns stored in party tables with role permissions in column_config
   - Two different storage patterns for similar data types

3. **Data Retrieval Complexity**:
   - Masterdata: Direct column access (e.g., `employee.first_name`)
   - Custom data: JSONB merge across 4 tables (requires special repository methods)

4. **RLS Policy Complexity**:
   - Need SELECT, UPDATE, INSERT policies on 4 tables × 5 roles = 60 policies
   - Policy management becomes error-prone
   - Recent bug: HR Admin blocked from editing due to missing UPDATE/INSERT policies

5. **Performance Concerns**:
   - Every employee fetch requires 4 additional queries to merge custom data
   - No indexes on JSONB keys (cannot index dynamic column names)
   - JOIN operations become complex with multiple party tables

### Proposed Architecture

**Consolidate all custom column data into the employees table** using JSONB columns:

```sql
ALTER TABLE employees
ADD COLUMN custom_data JSONB DEFAULT '{}'::jsonb;

CREATE INDEX idx_employees_custom_data_gin ON employees USING GIN (custom_data);
```

**Benefits:**

1. **Single Source of Truth**: All employee data (masterdata + custom) in one table
2. **Simplified Queries**: No multi-table merges required
3. **Consistent Permission Model**: All columns (masterdata and custom) use column_config.role_permissions
4. **Reduced RLS Policies**: Only need policies on employees table
5. **Better Performance**: Single query, GIN index for JSONB access
6. **Easier Debugging**: All data visible in one table query
7. **Simplified Repository Logic**: No special multi-table handling for HR Admin

## Dev Notes

### Data Migration Strategy

**Migration must preserve data integrity:**

```sql
-- Step 1: Add custom_data column
ALTER TABLE employees ADD COLUMN custom_data JSONB DEFAULT '{}'::jsonb;

-- Step 2: Migrate sodexo_data (first pass)
UPDATE employees e
SET custom_data = s.data
FROM sodexo_data s
WHERE e.id = s.employee_id;

-- Step 3: Migrate omc_data (merge with existing)
UPDATE employees e
SET custom_data = e.custom_data || o.data
FROM omc_data o
WHERE e.id = o.employee_id;

-- Step 4: Migrate payroll_data (merge with existing)
UPDATE employees e
SET custom_data = e.custom_data || p.data
FROM payroll_data p
WHERE e.id = p.employee_id;

-- Step 5: Migrate toplux_data (merge with existing)
UPDATE employees e
SET custom_data = e.custom_data || t.data
FROM toplux_data t
WHERE e.id = t.employee_id;

-- Step 6: Create index
CREATE INDEX idx_employees_custom_data_gin ON employees USING GIN (custom_data);

-- Step 7: Verify counts match
SELECT
  (SELECT COUNT(*) FROM sodexo_data) as sodexo_count,
  (SELECT COUNT(*) FROM omc_data) as omc_count,
  (SELECT COUNT(*) FROM payroll_data) as payroll_count,
  (SELECT COUNT(*) FROM toplux_data) as toplux_count,
  (SELECT COUNT(*) FROM employees WHERE custom_data != '{}'::jsonb) as employees_with_custom_data;

-- Step 8: Drop old tables (only after verification)
DROP TABLE sodexo_data;
DROP TABLE omc_data;
DROP TABLE payroll_data;
DROP TABLE toplux_data;
```

### Repository Simplification Example

**Before (complex multi-table logic):**

```typescript
async getAllCustomDataForEmployee(employeeId: string) {
  const tables = ['sodexo_data', 'omc_data', 'payroll_data', 'toplux_data'];
  let allData = {};

  for (const table of tables) {
    const { data } = await this.supabase
      .from(table)
      .select('data')
      .eq('employee_id', employeeId)
      .single();

    if (data) {
      allData = { ...allData, ...data.data };
    }
  }

  return allData;
}
```

**After (simple single-table query):**

```typescript
async getCustomData(employeeId: string) {
  const { data, error } = await this.supabase
    .from('employees')
    .select('custom_data')
    .eq('id', employeeId)
    .single();

  if (error) throw new RepositoryError('Failed to fetch custom data', error);
  return data.custom_data || {};
}
```

### RLS Policy Simplification

**Before (4 tables × multiple policies each):**

- CREATE POLICY "HR Admin can select sodexo_data" ON sodexo_data...
- CREATE POLICY "HR Admin can update sodexo_data" ON sodexo_data...
- CREATE POLICY "HR Admin can insert sodexo_data" ON sodexo_data...
- CREATE POLICY "Sodexo can select sodexo_data" ON sodexo_data...
- [Same 4 policies for omc_data, payroll_data, toplux_data = 16 policies]

**After (single table with JSONB filtering):**

- CREATE POLICY "Users can view employees" ON employees...
  - HR Admin: See all fields including custom_data
  - External parties: See custom_data filtered by column_config permissions in application layer

**Note:** Application-layer filtering via column_config.role_permissions handles which custom columns each role can access.
