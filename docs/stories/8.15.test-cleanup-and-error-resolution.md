## Dev Notes

### Architecture Context

This story focuses on resolving accumulated technical debt from test failures and build errors. The codebase has 236 failing tests in 34 files and 6 build/lint errors that need systematic resolution.

**Current Test Status:**

- Total failing tests: 236
- Affected test files: 34
- Build/lint errors: 6
- Test framework: Vitest
- Integration testing: Requires Next.js dev server running

**Common Test Failure Patterns:**

Based on typical HR Masterdata application issues:

1. **Authentication/Authorization Errors:**
   - Mock authentication not properly set up in tests
   - Supabase client not mocked correctly
   - RLS policy tests failing due to user context issues

2. **Component Rendering Errors:**
   - Missing context providers (AuthProvider, ThemeProvider, etc.)
   - Props type mismatches after component updates
   - Hook dependency issues (useEmployees, useImportantDates, etc.)

3. **API Route Test Errors:**
   - Request/response format changes not reflected in tests
   - Mock Supabase client methods out of sync
   - Route parameter handling changes

4. **Service/Repository Test Errors:**
   - Business logic updates not reflected in test expectations
   - Mock data structures outdated
   - Database query mocking issues

5. **Type Errors:**
   - Missing type definitions after story implementations
   - Incorrect type assertions in service layers
   - Type mismatches in repository methods

**Test Standards:**

1. **Naming Convention:**
   - Test files: `*.test.ts` or `*.test.tsx`
   - Test descriptions: "should [expected behavior] when [condition]"
   - Use describe/it blocks for grouping

2. **Mocking:**
   - Mock Supabase client using `vi.mock('@/lib/supabase/client')`
   - Mock authentication context for protected routes
   - Mock external services (date-capacity, termination-workflow, etc.)

3. **Assertions:**
   - Use `expect()` assertions from Vitest
   - Prefer specific assertions (`toHaveBeenCalledWith`) over generic (`toBeCalled`)
   - Test both success and error paths

4. **Cleanup:**
   - Use `beforeEach` and `afterEach` for setup/teardown
   - Reset mocks between tests: `vi.clearAllMocks()`
   - Clean up test data in integration tests

[Source: docs/architecture/testing-strategy.md]

### Common Fix Patterns

**1. Mock Supabase Client:**

```typescript
// Before
import { createClient } from '@/lib/supabase/client';

// Fix: Mock at top of test file
vi.mock('@/lib/supabase/client', () => ({
  createClient: vi.fn(() => ({
    from: vi.fn(() => ({
      select: vi.fn().mockResolvedValue({ data: [], error: null }),
      insert: vi.fn().mockResolvedValue({ data: {}, error: null }),
      // ... other methods
    })),
  })),
}));
```

**2. Component Provider Wrapper:**

```typescript
// Fix: Wrap component in required providers
import { render } from '@testing-library/react';
import { AuthProvider } from '@/lib/context/auth-context';

const renderWithProviders = (component) => {
  return render(
    <AuthProvider>
      {component}
    </AuthProvider>
  );
};

// In test
renderWithProviders(<EmployeeTable employees={mockEmployees} />);
```

**3. Type Null Safety:**

```typescript
// Before
const email = employee.email.toLowerCase(); // Error if email is null

// Fix: Add null check
const email = employee.email?.toLowerCase() ?? '';
```

**4. Async Test Handling:**

```typescript
// Before
it('should fetch employees', () => {
  const employees = await fetchEmployees(); // Error: await outside async
  expect(employees).toHaveLength(5);
});

// Fix: Make test async
it('should fetch employees', async () => {
  const employees = await fetchEmployees();
  expect(employees).toHaveLength(5);
});
```

### Performance Considerations

- **Test Execution Time:** Target <30 seconds for full unit test suite
- **Integration Tests:** May take longer (2-5 minutes) due to API calls
- **Parallel Execution:** Vitest runs tests in parallel by default
- **Flaky Tests:** Tests that fail intermittently should be fixed or isolated
- **Test Database:** Integration tests should use isolated test database

[Source: docs/architecture/testing-strategy.md]

### Risk Assessment

**High Risk Areas:**

1. Integration tests that modify database state (ensure proper cleanup)
2. Tests that depend on external services (should be mocked)
3. Tests with timing dependencies (use fake timers or proper async handling)
4. Tests that rely on specific data in database (should seed test data)

**Mitigation:**

- Run tests in isolation (each test should be independent)
- Use test database with known seed data
- Mock external dependencies
- Implement proper cleanup in afterEach hooks
