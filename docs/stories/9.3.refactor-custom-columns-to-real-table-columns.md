# Story 9.3: Refactor Custom Columns from JSONB to Real Table Columns

## Status **Ready for Review**

---

## Story

**As a** Technical Lead,  
**I want** custom columns to be implemented as real database columns on the employees table instead of JSONB key-value pairs,  
**so that** the system benefits from native database features (type safety, indexing, constraints) and a simpler, more maintainable architecture.

---

## Background & Context

### Current Architecture Issues

Story 9.2 consolidated custom column data from 4 party-specific tables into a single `employees.custom_data` JSONB column. While this was an improvement over the multi-table architecture, it still has limitations:

**Current State (Post-9.2):**

```sql
employees table:
  - id, first_name, surname, ssn, email, ...
  - custom_data JSONB = { "Sodexo_MealPlan": "Premium", "OMC_Training": true, ... }
```

**Problems with JSONB approach:**

1. **No Type Safety**: JSONB stores everything as JSON - no database-level type enforcement
2. **Weaker Indexing**: GIN indexes are less efficient than native B-tree indexes on typed columns
3. **Complex Queries**: Accessing data requires JSONB operators (`custom_data->>'column_name'`) instead of direct column access
4. **No Column Constraints**: Cannot enforce NOT NULL, CHECK constraints, or foreign keys on JSONB keys
5. **Over-Engineering**: The JSONB approach was designed for **self-service** column creation by external parties, but in reality **only HR Admins can create columns** via the Column Settings page

### Business Reality

**Column Creation is Controlled, Not Dynamic:**

- Only HR Admins have access to the Column Settings page (`/admin/columns`)
- External parties **cannot** self-service create columns
- External parties must **request** HR Admin to create columns for them
- Column creation is **infrequent** and **controlled** (not runtime dynamic)
- ~1,000 employees (not millions) - migrations are fast

This means custom columns behave more like **masterdata columns** (controlled, defined at design time) than truly dynamic user-defined fields.

### Proposed Architecture

**Treat custom columns like masterdata columns with real database columns:**

```sql
ALTER TABLE employees
ADD COLUMN sodexo_meal_plan TEXT,
ADD COLUMN omc_training_completed BOOLEAN,
ADD COLUMN payroll_bonus_amount NUMERIC(10,2),
ADD COLUMN toplux_vehicle_assigned TEXT;

-- Create indexes for performance
CREATE INDEX idx_employees_sodexo_meal_plan ON employees(sodexo_meal_plan);
CREATE INDEX idx_employees_omc_training ON employees(omc_training_completed);
```

**Benefits:**

1. ✅ **Type Safety**: Database enforces column types (TEXT, INTEGER, BOOLEAN, DATE, NUMERIC)
2. ✅ **Better Performance**: Native B-tree indexes instead of GIN indexes
3. ✅ **Simpler Queries**: `SELECT first_name, sodexo_meal_plan FROM employees` instead of `SELECT first_name, custom_data->>'Sodexo_MealPlan'`
4. ✅ **Standard SQL**: No special JSONB operators needed
5. ✅ **Column Constraints**: Can add NOT NULL, CHECK, DEFAULT values
6. ✅ **Better Tooling**: Database viewers show all columns clearly
7. ✅ **Consistent Architecture**: Custom columns and masterdata columns work identically
8. ✅ **Migration-Based Workflow**: HR Admin creates column → migration generated → deployed

**Trade-offs:**

- ⚠️ **Requires Migrations**: Each column add/delete/rename requires a database migration
- ⚠️ **Deployment Required**: Cannot add columns without deploying migration
- ✅ **Acceptable**: Since only HR Admin creates columns (infrequent, controlled process)

## Acceptance Criteria

1. **Remove JSONB Column & Cleanup**: Drop `employees.custom_data` column and delete all existing custom column definitions (clean slate)
2. **Column Creation Generates Migration**: When HR Admin creates a custom column, system generates and applies migration to add real column
3. **Column Deletion Generates Migration**: When HR Admin deletes a custom column, system generates and applies migration to drop column
4. **Column Rename Generates Migration**: When HR Admin renames a custom column, system generates migration to rename column
5. **Type Mapping**: Column types in column_config (text, number, date, boolean) map to PostgreSQL types (TEXT, NUMERIC, DATE, BOOLEAN)
6. **Repository Updated**: Custom data repository queries real columns instead of JSONB
7. **API Endpoints Updated**: Custom data endpoints read/write real columns
8. **Column Config Updated**: column_config.column_name enforces valid snake_case database column names
9. **Permissions Unchanged**: column_config.role_permissions continues to control visibility/edit permissions (application layer)
10. **Tests Pass**: All existing tests updated and passing

## Dev Notes

### Clean Slate Migration

**Existing custom columns will be deleted because:**

1. **Invalid Column Names**: Current columns have names like "Hotel Required?", "Room Number (Shared)", "Joining Instructions sent"
   - Contain spaces, parentheses, question marks, special characters
   - Cannot be used as PostgreSQL column names (would require quoted identifiers everywhere)
2. **No Production Data**: Confirmed that no production data exists in custom columns that needs preservation

3. **Fresh Start Benefits**:
   - Proper snake_case naming from day one
   - Clean architecture without legacy naming issues
   - External parties will re-enter data with correctly named columns

**Migration will:**

```sql
-- migrations/YYYYMMDD_remove_jsonb_custom_columns.sql
BEGIN;

-- Step 1: Remove all custom column definitions
DELETE FROM column_config WHERE is_masterdata = false;

-- Step 2: Drop JSONB column and index
DROP INDEX IF EXISTS idx_employees_custom_data_gin;
ALTER TABLE employees DROP COLUMN IF EXISTS custom_data;

-- Add note
COMMENT ON TABLE employees IS
  'Removed custom_data JSONB column. Custom columns now implemented as real table columns.';

COMMIT;
```

### Migration Workflow (Manual Approach)

**When HR Admin creates a new custom column:**

1. HR Admin enters column details in Column Settings UI:
   - Name: "Meal Plan"
   - Type: "text"
   - Category: "Sodexo"
2. System creates entry in column_config:

   ```sql
   INSERT INTO column_config (column_name, column_type, is_masterdata, category, role_permissions)
   VALUES ('sodexo_meal_plan', 'text', false, 'Sodexo', '{"sodexo": {"view": true, "edit": true}}');
   ```

3. UI shows message: "Column 'Meal Plan' created. Will be available after next deployment."

4. Developer creates migration:

   ```sql
   -- migrations/20251106000003_add_sodexo_meal_plan.sql
   ALTER TABLE employees ADD COLUMN sodexo_meal_plan TEXT;
   CREATE INDEX idx_employees_sodexo_meal_plan ON employees(sodexo_meal_plan);
   ```

5. Migration deployed via normal deployment process

6. Column becomes available to users

### Column Naming Convention

**Recommended format:** `{party}_{descriptive_name}`

Examples:

- `sodexo_meal_plan`
- `sodexo_accommodation_status`
- `omc_training_completed`
- `omc_certification_date`
- `payroll_bonus_amount`
- `payroll_tax_code`
- `toplux_vehicle_assigned`
- `toplux_license_expiry_date`

**Validation rules:**

- Lowercase only
- Snake_case (underscores, no spaces)
- No SQL reserved words
- No special characters except underscore
- Max 63 characters (PostgreSQL limit)

### Repository Query Example

**Before (JSONB):**

```typescript
const { data } = await supabase
  .from('employees')
  .select('id, first_name, surname, custom_data')
  .eq('id', employeeId)
  .single();

return data.custom_data || {};
```

**After (Real Columns):**

```typescript
// Get columns user has permission to view
const visibleColumns = await getVisibleColumnsForRole(userRole);
const columnNames = visibleColumns.map((c) => c.column_name).join(', ');

const { data } = await supabase
  .from('employees')
  .select(`id, first_name, surname, ${columnNames}`)
  .eq('id', employeeId)
  .single();

// Return only custom columns (exclude masterdata)
const customData = {};
visibleColumns.forEach((col) => {
  if (!col.is_masterdata) {
    customData[col.column_name] = data[col.column_name];
  }
});

return customData;
```

## Technical Risks & Mitigation

### Risk 1: Migration Errors

**Likelihood:** Medium  
**Impact:** High  
**Mitigation:**

- Test all migrations in staging first
- Use transaction-wrapped migrations (BEGIN/COMMIT)
- Keep migrations simple and focused (one column per migration)
- Document rollback procedures

### Risk 2: Column Name Conflicts

**Likelihood:** Low  
**Impact:** Medium  
**Mitigation:**

- Enforce unique constraint on column_config.column_name
- Validate column names don't conflict with existing columns
- Use party prefix for custom columns (e.g., `sodexo_*`)

### Risk 3: Breaking Changes

**Likelihood:** Medium  
**Impact:** High  
**Mitigation:**

- Comprehensive test coverage
- Staged rollout (staging → production)
- Monitor error logs post-deployment

### Risk 4: Data Loss from Clean Slate

**Likelihood:** N/A (Accepted)  
**Impact:** Low  
**Mitigation:**

- Confirmed no production data exists in custom columns
- External parties will need to re-enter custom column data after Story 9.3 completes
- Document this as known impact in deployment notes
- Coordinate with external parties about data re-entry
